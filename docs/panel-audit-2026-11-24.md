# 2026-11-24 后台与v8.1方案核对

## 结论与范围

当前是可运行的账户与媒体管理底座，**没有实现方案全部功能，不能认定为完整商业运营系统**。本次对照方案第19、22、25、27～30篇、实际源码、dmit-pro接口和浏览器页面检查；静态代码存在、接口成功、页面可用、真实外部业务验收是不同证据。

原始方案：[emby-cloud-plan](https://github.com/czy-code-923/emby-cloud-plan)。本次修复不引入新余额体系，不改账号权益，不开启注册、收费、Bot或公网管理入口。

## 本次修复与逻辑分工

1. 邀请管理打不开：已复现`nodes is not iterable`。V2返回`item.rows/roots/selected/page`，页面误读V1的`nodes/edges`。改用V2原生分页，搜索/根/折叠/详情均由服务端计算，每页100行，取消旧请求；没有降级为全量拉取再分页。原有单人、批量和子树维护仍走原鉴权/审计接口。
2. 卡码管理：原“注册码”实际管理注册、续期和白名单卡，以及邀请码记录，现改名“卡码管理”并解释职责。管理员发卡与用户个人邀请是两个来源；邀请续期码仍属于邀请来源，不能当普通发卡覆盖。
3. 个人邀请中心：只处理本人额度、邀请码与直属受邀关系；首屏改为一次可取消、不可缓存的`/api/v2/invite/summary`请求。全站关系维护仍位于邀请系统管理。
4. Telegram：修复页面引用不存在的`telegram_bot_token/enable_telegram`等字段。Bot收件总开关为`Global.telegram_mode`，Token为`Telegram.bot_token`，扫码登录另有`Telegram.login_enabled`。个人设置绑定的是人的身份，不是第二个服务Bot；指令管理使用同一配置；高级配置也编辑同一份数据。OpenStrm的Bot轮询保持关闭。连通测试会发送消息，按钮明确标明，本次未向任何人发送测试消息。
5. 域名：SSH/VPN管理无需公网域名。新增“站点与入口”，网站字段为`Global.public_base_url`，仅接受无凭据/路径/查询串的HTTPS域名；播放线路仍用原Emby公开地址字段，内部API地址不随之改动。保存不修改DNS/证书/端口/白名单，不显示虚假的已绑定状态。
6. 共享表单：取消加载后不再写入旧schema，防止页面切换时过期数据回填。

## 需要保留的边界

- 新邀请关闭时个人邀请页按功能开关隐藏；管理员历史维护和后端既有受邀用户续期/到期清理接口仍可用。若需要在关闭新邀请后长期提供个人历史维护，应另做独立维护入口，不能重新开启新邀请来代替。
- 本版本不启用付费交易、Telegram购买外链或付费码组合，不把普通卡码变成订单履约系统。
- 域名填写后仍需独立完成DNS、TLS、Origin/Host白名单、可信代理及Cookie配置，并验证救援入口；本次没有对公网新增管理监听。
- 已发布的完整源码仅覆盖当前程序；Emby本体遵循厂商闭源许可。上游能力不等于v8.1全部业务已完成。
